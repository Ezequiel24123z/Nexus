# Ronda B2 — almacenamiento incremental opcional

18 de septiembre de 2026. Continuación de B1. Implementado y probado con datos aislados; no se ha migrado el almacén real del usuario, reiniciado su aplicación ni empaquetado un instalador.

## Qué cambia

Configuración → Almacenamiento local permite preparar y confirmar la activación de SQLite. Sólo se permite sin ejecuciones, colas o compresiones en curso. También permite exportar el estado actual a JSON compatible, sin sobrescribir los archivos internos del almacén. No utiliza llamadas al modelo.

Se separan raíz, metadatos de tareas y registros de mensajes, conversación, eventos, llamadas y efectos. Cada transacción escribe las filas modificadas; los eventos locales del motor identifican la tarea afectada para no serializar los historiales de las demás. El modo JSON anterior continúa siendo el predeterminado hasta la activación explícita.

### Activación y protección de datos

1. Guardar estado JSON y crear una copia previa única con sincronización a disco.
2. Crear una base SQLite nueva, copiar los datos y comprobar igualdad de todos los campos durables al leerlos de nuevo. Los campos visuales transitorios de streaming no son historial confirmado.
3. Cerrar la base candidata y seleccionar el formato mediante un marcador atómico `storage-engine.json`. Hasta ese punto, el JSON sigue siendo el almacén seleccionado.
4. Mantener `workspace.json` congelado y `workspace.before-sqlite-<uuid>.json`. Los cambios nuevos van a `workspace-v1-<uuid>.sqlite`.

Si falla la apertura después de activar, se bloquean guardados hasta reiniciar: no se vuelve a escribir silenciosamente el JSON anterior. Si la base seleccionada falta o está corrupta, el arranque informa del error, conserva archivos y no crea un historial vacío. Si un ejecutable antiguo modifica el JSON congelado, se detecta al abrir y se detiene para revisar ambos historiales.

Se comprueba la revisión dentro de cada transacción con cambios, evitando que un segundo escritor sobrescriba una revisión más reciente. Las copias SQLite usan `VACUUM INTO`, no una copia del archivo activo sin su WAL. Se crean durante guardados, como máximo una por hora, conservando las 24 más recientes. No hay servicio de copias con la app cerrada.

La importación de instalaciones antiguas omite orígenes ya migrados a SQLite: su JSON está desactualizado. Si el destino usa SQLite, la copia previa a importar refleja su estado actual, no su JSON congelado. Los orígenes omitidos no generan copias repetidas.

## Límites y recuperación

- El adaptador es síncrono y el historial completo sigue cargado en memoria. Se recorre y serializa el historial de la tarea modificada para comparar registros. La migración y las copias pueden bloquear temporalmente el proceso principal. Sacar I/O a un trabajador y cargar páginas desde disco siguen pendientes.
- La configuración usa esquema de aplicación 4; SQLite usa esquema de almacenamiento 1. No son la misma versión.
- `node:sqlite` está disponible en los runtimes probados y aún emite aviso experimental. No se añade otra dependencia nativa.
- No se ha ensayado un corte eléctrico real ni se promete resistencia a cualquier fallo de disco. SQLite usa WAL y `synchronous=FULL`; esas opciones no sustituyen las pruebas de hardware. Referencias oficiales: [WAL](https://www.sqlite.org/wal.html), [PRAGMA synchronous](https://sqlite.org/pragma.html#pragma_synchronous), [SQLite en Node](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html).
- Los JSONL y checkpoints siguen siendo registros auxiliares. No hay dos almacenes principales actualizándose en paralelo.
- No existe todavía un botón de restauración ni reversión automática a JSON. La exportación es de estado, no una copia portable completa: no incluye binarios adjuntos, archivos de proyecto ni claves cifradas. Conversaciones e instrucciones pueden contener información privada; revisar antes de compartir.

Ante problemas, conservar toda la carpeta de datos, incluidos marcador, base y archivos `-wal`/`-shm` existentes. No sustituir la base ni borrar el marcador para forzar el arranque: el JSON previo no contiene trabajo posterior a la migración. Con la aplicación operativa, usar exportación compatible y conservar también `tasks`, `uploads`, proyectos y las copias locales de credenciales. La restauración se debe verificar primero en una carpeta aislada. Para una copia de archivos completa, cerrar la app; no copiar únicamente una base activa ignorando su WAL.
